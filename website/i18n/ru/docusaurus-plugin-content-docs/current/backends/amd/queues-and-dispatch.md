# Очереди и диспетчеризация

Диспетчеризация ядра означает запись командных пакетов в кольцевой буфер и
звонок в doorbell (дверной звонок). Эта страница описывает механику кольца
(`AmdComputeQueue`), per-owner связку, которая его оборачивает (`AmdConnector`),
две стратегии диспетчеризации (одноочередная против многоочередной), примитив
завершения (`Timeline`) и каждую переменную окружения, конфигурирующую бэкенд.

Форма этого дизайна вытекает из одного факта: **tinygrad сериализован через
GIL** — одна compute-очередь на устройство, и GIL в Python делает каждую
диспетчеризацию атомарной. Svod убирает GIL, чтобы получить настоящую
параллельность, поэтому инварианты, которые давал GIL, приходится
перестраивать явно. Результат — путь диспетчеризации, который может быть
свободным от блокировок.

## Командное кольцо: `AmdComputeQueue`

`device/src/amd/queue.rs` определяет `AmdComputeQueue`, который владеет:

- **16-мегабайтным видимым хосту кольцом** (`COMPUTE_RING_BYTES`) — командные
  пакеты пишутся прямо в него со стороны CPU;
- **doorbell** (`*mut u64` MMIO) — командному процессору GPU сообщают о «новой
  работе», записывая сюда новый write-индекс;
- GART-резидентными слотами **write/read dispatch-id** — KFD читает указатель
  записи в дополнение к doorbell, поэтому он публикуется первым.

### PM4 против AQL

Существуют два формата пакетов «на проводе», выбираемые один раз при создании
очереди из числа XCC устройства:

```text
will_use_pm4(core) = !SVOD_AMD_AQL && num_xcc == 1
```

- **PM4** (single-XCC: дефолт gfx11/12) — сырые PM4-dword'ы, записываемые прямо
  в кольцо (`KFD_IOC_QUEUE_TYPE_COMPUTE`). В doorbell звонят следующим индексом
  dword.
- **AQL** (multi-XCC CDNA) — 64-байтные AQL-пакеты
  (`KFD_IOC_QUEUE_TYPE_COMPUTE_AQL`), с PM4-хелперами, обёрнутыми внутрь
  AQL vendor-IB пакетов. В doorbell звонят последним завершённым слотом
  (`write_idx - 1`).

Одна PM4-диспетчеризация — это фиксированная последовательность, зеркалящая
`hcq.py:371-378` из tinygrad:

```text
wait(timeline, prev)  →  hdp_flush  →  acquire_mem  →  exec  →  release_mem(timeline, next)
```

`exec` — это поток `SET_SH_REG`, который загружает адрес шейдера, регистры
`RSRC1/2/3`, дескриптор scratch и `TMPRING_SIZE`, SGPR'ы `USER_DATA`, размеры
запуска, а затем `DISPATCH_DIRECT`, за которым следует `CS_PARTIAL_FLUSH`.
Завершающий `release_mem` записывает значение таймлайна этой диспетчеризации в
слот сигнала коннектора, когда GPU её заканчивает.

### Свободная от блокировок внутренняя изменяемость

`AmdComputeQueue.inner` — это `UnsafeCell<QueueInner>`, а не `Mutex` —
диспетчеризация мутирует его через `&self` без блокировки. Это корректно
благодаря **инварианту единственного владельца**: на время жизни
`ConnectorLease` ровно один поток выдаёт последовательную, нереентерабельную
диспетчеризацию в очередь (тот же паттерн, что `RawBuffer` использует в
`device/src/allocator.rs`). Общий поток дренажа никогда не трогает очередь — он
читает только таймлайн (см. ниже). Очереди разных коннекторов чередует
аппаратный планировщик GPU (MES — MicroEngine Scheduler), а не CPU-блокировка.

### Back-pressure кольца

Хост, работающий с `wait=false` быстрее, чем GPU успевает дренировать кольцо,
обогнал бы 16-мегабайтное кольцо на круг и перезаписал бы ещё не потреблённые
пакеты. `wait_dispatch_headroom` предотвращает это, ограничивая число
неотозванных диспетчеризаций величиной `RING_MAX_INFLIGHT` (половина кольца) и
блокируясь на **сигнале таймлайна**, когда граница достигнута:

```rust
let last_reserved = conn.timeline_value().saturating_sub(1);
if last_reserved > RING_MAX_INFLIGHT {
    let target = last_reserved - RING_MAX_INFLIGHT;
    conn.timeline_signal().wait_signal_value(target, 30_000)?;
}
```

Проверка опирается на сигнал таймлайна — проверенный примитив завершения — а не
на PM4 read-указатель, чья семантика для COMPUTE-очереди ненадёжна и загнала бы
спин в дедлок.

## Per-owner связка: `AmdConnector`

Одной очереди недостаточно для диспетчеризации. `AmdConnector`
(`device/src/amd/connector.rs`) связывает всё, что нужно одному независимому
вызывающему:

| Поле | Что это |
|---|---|
| `queue: Box<AmdComputeQueue>` | Кольцо + doorbell + GART (единственный владелец → без блокировок) |
| `arena: Box<KernargArena>` | 16-мегабайтная GTT bump-арена kernarg |
| `scratch_state: Mutex<ScratchState>` | Подложка scratch для спилла регистров, растёт по запросу |
| `timeline: Arc<Timeline>` | Монотонный счётчик + сигнал завершения |

Каждый `ExecutionPlan` и каждый `AmdGraph` владеет своим собственным
коннектором. То, что очередь и арена держатся за `Box`, а не за `Arc` —
несущая деталь: это доказывает, что нет второго хэндла, алиасящего
`UnsafeCell`, а именно это делает свободную от блокировок диспетчеризацию
корректной. Арена своя у каждого коннектора, поэтому её bump-курсор и таймлайн
коннектора подчиняются одному порядку — обёрнутый по кругу слот kernarg
доказуемо свободен, как только этот таймлайн дренируется.

`ensure_has_local_memory(private_segment_size)` увеличивает scratch-буфер,
когда свежезагруженному ядру нужно больше байт на поток, чем сейчас выделено
(выделить новый → swap → дренировать → освободить старый). Scratch — это
VRAM, доступная только GPU, переаллоцируемая динамически и исторически бывшая
источником сбоев `NotPresent` — см. [Отладку](./debugging.md).

## Две стратегии диспетчеризации

Per-device enum `Dispatcher` (`device/src/amd/device.rs`) выбирает, как
владельцы получают коннектор и сериализуется ли диспетчеризация. Он строится
один раз при открытии устройства по значению `SVOD_AMD_SINGLE_QUEUE`:

### Одноочередная (по умолчанию)

```text
SVOD_AMD_SINGLE_QUEUE не задана или ≠ 0
```

Все владельцы делят **один** коннектор на физическое устройство, а
диспетчеризация и scratch-realloc сериализованы за `Mutex<()>`, взятым через
`exec_guard()`. Тогда ядро всегда видит лишь одну compute-очередь на GPU —
модель tinygrad.

Это **KFD-безопасный** режим, и он стоит по умолчанию по конкретной причине:
тяжёлая параллельная многоочередная диспетчеризация **перегружает планировщик
MES/runlist в ядре и может его уронить**. У одного GPU один командный процессор,
и он всё равно выполняет диспетчеризации последовательно; многоочередность лишь
накладывала друг на друга сборку пакетов на стороне CPU, что и загнало KFD на
плохой путь. Одноочередный режим убирает этот краш.

### Многоочередная (opt-in)

```text
SVOD_AMD_SINGLE_QUEUE=0
```

Каждый владелец арендует **эксклюзивно принадлежащий** коннектор из пула
простаивающих (ограниченного `CONNECTOR_POOL_CAP = 4`); MES чередует N
очередей, так что диспетчеризации не нужна CPU-блокировка, и `exec_guard()`
возвращает `None`. Именно эксклюзивность и неалиасируемость аренды не дают двум
диспетчерам делить одну KFD-очередь.

:::caution Оговорка о перегрузке ядра
Многоочередный режим — это свободный от блокировок, максимально параллельный
путь, но именно он перегружает KFD под нагрузкой. По этой причине он opt-in.
Настоящее решение — владеть GPU так, чтобы ядро никогда не было на пути
диспетчеризации — это [userspace-драйвер AM](./am-driver.md).
:::

### `ConnectorLease`

`lease_connector` возвращает `ConnectorLease` — не-`Clone` хэндл, который
`Deref`-ится в `&AmdConnector`, так что вызывающим не важен режим. При
дропе `return_connector` делает то, что нужно для текущего режима: возвращает
коннектор в пул (многоочередный режим, до предела) или ничего (одноочередный
режим — разделяемый коннектор живёт на ядре). При дропе он **не**
синхронизируется; `Timeline` коннектора остаётся зарегистрированным, так что
дренаж на уровне всего устройства его всё равно покрывает.

## Примитив завершения: `Timeline`

`Timeline` (`device/src/amd/signal.rs`) — это монотонный счётчик `AtomicU64`
плюс GTT-когерентный слот `AmdSignal`, который GPU пишет при завершении
диспетчеризации. Это **единственный примитив, пересекающий владельцев**:

- коннектор *диспетчеризует* в него — `next()` делает `fetch_add(1)`, чтобы
  зарезервировать значение, которое запишет его пакет `release_mem`;
- любой поток может его *дренировать* — `drain()` читает атомик и опрашивает
  слот сигнала, **ни разу не трогая очередь**.

Именно эта развязка держит диспетчеризацию свободной от блокировок.
Ядро устройства (`AmdDeviceCore`) держит `Weak<Timeline>` для каждого
коннектора — а не `Weak<AmdConnector>` — так что `synchronize_all` (барьер
перед любым хостовым чтением или освобождением буфера) дренирует всю работу «в
полёте» исключительно через эти атомики:

```text
AmdDeviceCore.synchronize_all():
   for each live Timeline:  timeline.drain(30s)   // только атомики + слот сигнала
```

`AmdSignal::wait_signal_value` опрашивает ярусами — плотный спин → `yield_now`
→ сон через KFD `WAIT_EVENTS` после 200 мс — так что долгое или зависшее
ожидание не сжигает CPU, а сбой GPU во время ожидания всплывает немедленно, а
не блокирует на весь 30-секундный таймаут.

:::note Заворот 2³²
PM4 `WAIT_REG_MEM`/`RELEASE_MEM` сравнивают младшие 32 бита слота сигнала,
поэтому счётчик должен оставаться ниже 2³². `ensure_timeline_headroom`
дренирует и сбрасывает на отметке 2³¹ (`TIMELINE_WRAP_WATERMARK`) перед
резервированием каждого значения, так что долгий цикл `wait=false` не может
перевалить за 2³² и породить ложный таймаут.
:::

## Шов

Все четыре ядерные операции, нужные слою очередей, маршрутизируются через трейт
[`AmdIface`](./overview.md) на ядре устройства:

```rust
pub trait AmdIface: Send + Sync + std::fmt::Debug {
    fn alloc_raw(&self, size, kind, tag, cpu_access, zero) -> Result<AllocResult>;
    fn free_raw(&self, gpu_va, size, handle);
    fn setup_ring(&self, desc: &RingDesc) -> Result<QueueHandle>;
    fn teardown_ring(&self, queue_id: u32);
    fn wait_events(&self, timeout_ms: u32) -> Result<Option<Error>>;
}
```

Обратите внимание, чего *нет* в трейте: кольцо, GART, EOP и ctx-save буферы —
все выделяются выше шва (через `alloc_raw`) внутри `create_queue`. Трейт только
**активирует** очередь — `setup_ring` выдаёт `CREATE_QUEUE` и `mmap`-ит
doorbell поверх кольца, которым верхняя половина уже владеет. На сегодня
`KfdIface` — единственная реализация.

## Справочник по конфигурации

Каждая переменная окружения, влияющая на AMD-бэкенд:

| Переменная | По умолчанию | Эффект |
|---|---|---|
| `SVOD_DEVICE` | `CPU` | Выбирает устройство по умолчанию для тензоров. Установите `SVOD_DEVICE=AMD:0`, чтобы работать на первом AMD GPU |
| `SVOD_AMD_BACKEND` | `kfd` | Выбор бэкенда. Сегодня принимается только `kfd`; `am` — это будущий шов (ошибка, если задан) |
| `SVOD_AMD_SINGLE_QUEUE` | `1` (вкл) | `=0` включает свободную от блокировок многоочередную диспетчеризацию; иначе KFD-безопасный одноочередной режим |
| `SVOD_AMD_AQL` | `0` (выкл) | `=1` принудительно включает AQL-пакеты даже на single-XCC железе — чтобы локализовать проблемы PM4 против AQL делением пополам |
| `SVOD_JIT_GRAPH` | не задана | Включает захват/переигрывание PM4-графа (также требует многоочередного режима). См. [Компиляцию и граф](./compile-and-graph.md) |
| `SVOD_KFD_TOPOLOGY` | путь sysfs | Переопределяет корень топологии, для тестирования без железа |
| `SVOD_DEBUG_DISPATCH` | не задана | Выводит для каждой диспетчеризации VA ядра / сетки / kernarg / scratch / буфера. См. [Отладку](./debugging.md) |
| `SVOD_DUMP_AMD_IR` | не задана | Если задана как директория, выгружает туда AMD LLVM IR каждого ядра |

:::caution Никакой `SVOD_AMD_MAX_QUEUES` не существует
Размер пула простаивающих коннекторов в многоочередном режиме — это
compile-time константа `CONNECTOR_POOL_CAP = 4` в `device.rs`, а не переменная
окружения.
:::

## Почему это важно

GIL давал tinygrad атомарную критическую секцию диспетчеризации бесплатно. Svod
перестраивает эту гарантию тремя способами: **единоличное владение** кольцом
(без блокировки диспетчеризации), **разделяемый сигнал таймлайна** для дренажей
(только атомики, никогда не очередь) и **явный back-pressure кольца**.
Одноочередный режим по умолчанию держит ядро в безопасности уже сегодня;
свободный от блокировок многоочередной путь готов к моменту, когда [драйвер
AM](./am-driver.md) целиком уберёт ядро из контура.
